# Décisions déjà prises et hors périmètre

Ne pas rouvrir une décision sans raison. Toute nouvelle décision de Pierre s'ajoute ici, datée.

| Décision | Pourquoi |
|---|---|
| Spot, ordres au marché, pas de levier ni de short | Perte bornée à la mise, simplicité |
| Exchange cible : `bitvavo`, choisi le 2026-10-04 | Raison : à compléter par Pierre. Éléments relevés ce jour-là : taker du premier palier 0,25 % (page officielle, contre 0,80 % chez Kraken Pro), marchés en EUR, minimum d'ordre de 5 € (confirmé par Pierre), agrément MiCA via l'AFM néerlandaise selon des sites tiers (à vérifier sur le registre ESMA) |

| L'app de bureau est visionneuse **et** superviseur (démarrer/arrêter les bots) | Décision de Pierre. Actions dans le menu natif et la zone de notification seulement (voir invariant 10) |

| Distribution : version portable + semi-installeur (venv créé et dépendances téléchargées au premier lancement) | Décision de Pierre. Pas de Python embarqué par PyInstaller. Réalisé le 2026-10-04 (F4) sous forme d'un dossier ou d'un zip, pas d'un exécutable unique auto-extrait : ce dernier s'extrait dans le dossier temporaire à chaque lancement, ce qui contredit « rien dans le dossier utilisateur » (choix de Claude, à confirmer par Pierre) |
| But de l'application : rapporter de l'argent à l'utilisateur ; le bot doit survivre, se cloner, viser une croissance composée (2026-10-04) | Décision de Pierre. Sa mort signifie qu'il ne gagne pas plus qu'il ne dépense en API. Ce n'est pas une promesse de gain : tout se juge en paper et par backtest |
| Le loyer d'API sort de la mise : kill switch, plus-haut et paliers jugent l'equity nette du loyer (2026-10-04) | Décision de Pierre. Sans cela un bot en cash qui appelle le LLM ne mourait jamais |
| Clonage par variantes, inspiré d'automaton : le parent transmet une note de stratégie, une graine aléatoire fait varier les paramètres ; l'enfant est financé par les gains du parent, jamais par de l'argent neuf (2026-10-04) | Décision de Pierre. L'agent propose, le code dispose ; pas d'auto-modification du code |
| Caisse de l'utilisateur : part des gains mise de côté, configurable, 50/50 pour commencer (2026-10-04) | Décision de Pierre. Écriture comptable, aucun retrait ni transfert dans le code |
| Un bot à l'arrêt sans issue ne meurt pas tout seul : il est signalé, le code dresse le bilan et conseille, l'utilisateur décide (2026-10-04) | Décision de Pierre. Il juge au vu de ce que l'agent a rapporté et consommé |
| Réveil sur mouvement de prix obligatoire quand l'agent dort en détenant une position (2026-10-04) | Décision de Pierre. Sinon la position n'est surveillée que par le kill switch pendant le sommeil |
| Tailles desserrées : un ordre jusqu'à 40 % de l'equity, 60 % par symbole, 80 % d'exposition totale inchangés (2026-10-04) | Décision de Pierre, sur proposition de Claude : à 20 % par ordre, les positions de 10 € ne pouvaient pas couvrir le loyer, et le modèle de risque conseillait souvent davantage. Essai gratuit du témoin `quant` sur sept mois : +16,6 % en somme contre +9,9 %, pire mois −2,8 % contre −2,0 % |
| Les outils d'analyse sont des modèles mathématiques dans le code, qui lisent les prix, calculent et alimentent tous les agents (2026-10-04) | Décision de Pierre. Le code calcule, les agents décident ; le témoin `quant` (sans LLM) est la référence à battre |
| Le LLM monte d'un étage : superviseur du témoin `quant`, qui trade (2026-10-04) | Décision de Pierre après l'évaluation réelle sur sept mois (`llm` +6,26 €, `quant` +7,80 € sans loyer : le LLM n'apportait rien par-dessus les modèles). Le LLM ne donne plus qu'une posture parmi quatre et des symboles autorisés, environ une fois par jour |
| Les postures sont des multiplicateurs fixés en code : offensive ×2, normale ×1, défensive ×0,5, pause = tout vendre (2026-10-04) | Proposition de Claude, à confirmer par Pierre au vu des backtests. Le LLM choisit un mot, pas un montant ; les garde-fous plafonnent toujours chaque ordre |
| Un appel raté du superviseur n'est pas une erreur de cycle : le cœur trade quand même (2026-10-04) | Sortir doit rester possible quand l'API est en panne. Contrepartie : une panne durable de l'API ne met pas le bot en `halted`, il continue comme `quant` ; la directive tombe d'elle-même après 48 h |
| Flux d'information : rien que des nombres, lus par le code, donnés au superviseur (2026-10-04) | Décision de Pierre (« le flux d'information est à mettre en place »). Indice Fear & Greed, taux de financement, calendrier macro. Pas de texte extérieur dans un prompt (injection) ; pas d'actualités tant qu'aucune source datée n'est vérifiée |
| L'application reste en lecture seule pour l'instant ; réglage de la température de l'agent à terme (2026-10-04) | Décision de Pierre |
| Paliers : 15 % / 25 % / mort à 40 % de drawdown ou 50 % de perte totale | On réduit la voilure avant la mort |
| Quarantaine **asynchrone** (future) | Attendre la confirmation ne doit pas bloquer les contrôles du kill switch |
| Mise réelle maximale : 50 € | Uniquement de l'argent que Pierre accepte de perdre à 100 % |
| Cap du projet : un « board » de trading. Plusieurs sous-agents quant différents émettent des positions cibles, **un seul portefeuille** les additionne (2026-10-05) | Décision de Pierre. Les stratégies différentes ne perdent pas en même temps ; un capital par sous-agent est impossible avec un ordre minimal de 5 € ; deux signaux opposés s'annulent sans frais. La mise de départ peut être relevée si le board le demande (en paper ; la mise réelle maximale de 50 € n'est pas rouverte) |
| Le sommet du board répartit le capital entre les stratégies par une **règle codée** d'abord ; un LLM à cette place (local, idée de Pierre) ne sera essayé qu'ensuite, si la mesure du levier « répartition » le justifie (2026-10-05) | Décision de Pierre, sur proposition de Claude. Le superviseur LLM a échoué sur le levier « taille », qui valait peu ; on mesure la valeur d'un levier avant d'y mettre un LLM |
| Clonage : la sélection des variantes se fait **en paper et en direct d'abord**, le capital ne va qu'aux survivantes (2026-10-05) | Décision de Pierre, sur proposition de Claude. Juger des variantes tirées au hasard sur le passé fabrique du surapprentissage ; sans LLM dans la décision, une variante en paper ne coûte rien |
| Règle de mort d'un agent : fin de vie s'il ne peut plus réinvestir ou s'il est déficitaire (2026-10-05) | Décision de Pierre. Seuils validés le même jour, à affiner après les essais à blanc : mort rapide inchangée (−40 % depuis le plus haut, −50 % de la mise) ; déficitaire = equity sous la mise à la fin d'une fenêtre de 90 jours **et** résultat inférieur à celui de `buyhold` sur la même fenêtre (variante retenue après le contrôle de `quant` : sous la mise seule, la règle aurait tué un agent qui protégeait la mise dans un marché à −40 %), jugée à partir du 90e jour de vie ; ne peut plus réinvestir = achats bloqués par le palier défensif pendant 30 jours d'affilée. Remplace « un bot à l'arrêt sans issue ne meurt pas tout seul ». Touche l'invariant 2 ; pas encore codé |
| Deuxième siège du board : rien pour l'instant, puis force relative BTC/ETH, puis univers élargi à une dizaine de cryptos (2026-10-05) | Décision de Pierre après une recherche d'état de l'art. Le retour à la moyenne est écarté : la littérature trouve du momentum sur les grandes cryptos, pas du retournement. Aucun candidat n'a de preuve solide à 0,6 % l'aller-retour ; chaque essai sera une seule variante déclarée d'avance |
| Les sous-agents du board tiennent des cibles en quantité, qui s'additionnent ; le capital n'est pas partagé (2026-10-05) | Décision de Pierre, sur proposition de Claude. Une cible en pourcentage ferait retailler à chaque mouvement de prix ; partager le capital diviserait ce que le sous-agent tendance gagne déjà. Une vente décidée et possible (au moins l'ordre minimal) reste due et passe avant toute entrée |
| Le board tourne en paper en direct (profil `board`) ; son état est en base et suit la vie ; une position que personne ne réclame est vendue, au démarrage comme à tout autre cycle, dès qu'elle vaut au moins l'ordre minimal (2026-10-05) | Décision de Pierre. Les treize mois de backtest sont tous vus : le paper en direct est le seul vrai hors-échantillon. Vendre l'orpheline est le choix le plus simple et le plus sûr (retour au cash, un ordre de frais) |
| Cap : l'application doit tourner 24 h sur 24 et être la plus rentable possible (2026-10-05) | Décision de Pierre, inscrite dans `CLAUDE.md`. Chaque proposition se juge sur la disponibilité et sur le résultat net de frais, sans toucher aux invariants |
| `reset` est refusé tant qu'un `run` tient la base (2026-10-05) | Feu vert de Pierre. Le bot vivant garde soldes et état en mémoire et les réécrivait après le reset : la nouvelle vie héritait de l'ancienne |
| Nettoyage : le superviseur LLM, les flux d'information et les agents de backtest `dca` et `momentum` sont retirés du code (2026-10-05) | Décision de Pierre (« maintenir des reliques abandonnées ? »). Le superviseur a échoué en backtest réel, la littérature donne peu de crédit aux flux, `dca` et `momentum` n'ont jamais servi de référence. Les résultats restent dans `etat.md`, le code dans l'historique git (dernier commit qui les contient : `6f52c3d`). L'agent `llm` est gardé : un LLM au sommet du board reste à essayer. Les lignes plus haut sur le superviseur, ses postures et ses flux décrivent donc du code retiré |

## Hors périmètre (sauf décision explicite de Pierre)

Levier, marge, futures, vente à découvert · retrait ou transfert de fonds par le code · agent qui modifie son code, ses garde-fous ou sa config · agent qui peut ajouter de l'argent neuf ou relever sa mise (le clonage décidé le 2026-10-04 ne finance un enfant qu'avec les gains du parent) · UI exposée au réseau, ou page web avec des boutons d'action (le démarrage/arrêt par le menu natif de l'app de bureau est, lui, décidé : axe F) · mise réelle au-delà de 50 € · promesse de rendement ou conseil de placement présenté comme fiable.
